# Kids Launcher — Project Context for Claude Code

## What this is

An Android home screen for a kid's phone that is also, in the same process, the [Device Owner](https://developer.android.com/work/dpc/build-dpc) parental-control agent. Package `com.kidslauncher.mdm`. It speaks directly to [`kid-phone-server`](https://github.com/siesta5787/kid-phone-server) (a separate repo) - there is no other server, protocol, or MDM stack involved; an earlier prototype used something else entirely and has been fully retired.

Originated as a fork of Josia Pietsch's µLauncher, itself descended from Finn Glas's Launcher, but almost nothing of that lineage remains functionally: the gesture-binding system, Minimalist Mode (as an optional toggle), torch, private-space lock, and audio-track controls were all removed. What's still genuinely shared is the app-list screen (`ui/list/`, `apps/`) - see `LICENSE-MIT-UPSTREAM`. Don't describe this project as "a fork" in user-facing copy; it's its own thing now built on a small inherited component, not vice versa.

## Tech stack

Kotlin, single Gradle module (`app/`). `minSdk = 34`, `compileSdk`/`targetSdk = 36`. Retrofit + kotlinx.serialization (`JsonNamingStrategy.SnakeCase`, matching the server's plain snake_case JSON) for the device-facing API client in `server/`. `androidx.preference` for Settings, `eu.jonahbauer.android.preference.annotations` (kapt-generated) for the typed `LauncherPreferences` accessor API.

**One Java file**: `preferences/LauncherPreferences$Config.java` - not a choice made in this fork, Josia Pietsch wrote it in Java originally (Sept 2024). It's the annotation config kapt reads to generate the real `LauncherPreferences` class every `mdm.xxx()` call in the codebase goes through - keep editing it in Java when adding new preference entries rather than converting it, since deeply-nested annotation arrays through kapt's Kotlin→Java stub bridge is a real source of subtle bugs that writing it directly in Java sidesteps.

## Architecture

- **Device Owner is the whole point.** `MdmDeviceAdminReceiver` + `dpm.isDeviceOwnerApp()` gate every enforcement call in `server/AppEnforcer.kt` - it's a no-op if not device owner, so it's safe to ship before a phone is actually provisioned.
- **`server/MdmSyncWorker.kt`** is the heartbeat: self-chains one-time `WorkManager` requests every 2 minutes (not `PeriodicWorkRequest`'s 15-minute floor - too slow for a parent to see a change land) to fetch policy, evaluate the lock decision, call `AppEnforcer.apply()`, and report status. `performMdmSync()` is also called directly by the Settings "Sync now" button and returns `Boolean` (whether it actually reached the server) so that button can show an honest success/failure toast.
- **`server/AppEnforcer.kt`** is the enforcement engine: suspends/hides packages not on the allowlist, engages/disengages lock-task kiosk mode (only when both an allowlist AND `kioskDesired` are set - never pins with zero allowed packages), applies the `lockTaskFeatures` bitmask, and applies WiFi/Bluetooth `UserManager` restrictions. `controllablePackages()` is the safety-critical bit - see gotchas below.
- **Offline override PIN** (`server/OfflineOverride.kt`): PBKDF2-HMAC-SHA256 verified fully offline against a hash+salt cached from the last successful sync. `verifyPin()` (pure verification, tracks failed attempts/lockout) is separate from `activate()` (the actual "lift restrictions for 2 hours" side effect) specifically so the Settings PIN-gate can reuse verification without also triggering an unwanted override.
- **Settings is PIN-gated** (`ui/settings/SettingsActivity.kt`) behind the same PIN if one's configured - shown as a non-cancelable modal dialog over the normally-inflated (but `INVISIBLE` until verified) content, not by deferring `binding` initialization, because `UIObjectActivity`'s `onStart()` unconditionally calls `setOnClicks()` which needs `binding` to already exist.
- **`restrictions_paused`** is a separate, manually-toggled kill-switch (unlike the PIN override, does *not* auto-clear on sync or after a timer) - an emergency escape hatch if a policy or launcher update ever ships something broken. Toggling it in Settings re-runs `AppEnforcer.apply()` and `reevaluateLockReasonFromCache()` immediately and offline, rather than waiting for the next sync.
- **`LockActivity.kt`** is the full-screen bedtime/screen-time block, with a visible (not hidden-behind-a-gesture) "Enter unlock code" button - the PIN itself is the security boundary, not the button's obscurity.
- **Silent self-update is unified with third-party app updates** - the launcher is just another row in kid-phone-server's `tracked_apps` table (package `com.kidslauncher.mdm.debug`, GitHub-sourced, `include_prereleases` on since it only ever publishes to a rolling `pre-release` tag), going through the exact same `AppInstaller`/`AppInstallReceiver`/`checkForTrackedAppUpdates` path as everything else via Device Owner's `PackageInstaller` privilege - no launcher-specific update code exists anymore (the old `LauncherUpdater`/`LauncherUpdateInstallReceiver`/`launcher_releases` system was fully retired). The one place self-update still differs from a third-party install: `AppInstallReceiver` skips deleting its cache file on success when the installed package is this app itself, since installing over yourself can kill/replace the process before that line gets to run. A release that already failed to install is cached per-package in `TrackedAppUpdateState` (`tracked_app_update_state` preference) so it isn't retried every 2 minutes forever - covers the launcher the same as any tracked app now.

## Non-obvious gotchas (hit for real, more than once in some cases)

- **`PackageManager` query methods silently exclude apps hidden via `dpm.setApplicationHidden()` unless you pass `MATCH_UNINSTALLED_PACKAGES`.** This bit `AppEnforcer.controllablePackages()`'s `getInstalledApplications()` call *and*, separately, `MdmSyncWorker.collectInstalledApps()`'s `getApplicationInfo()` call one level deeper - fixing only the first still left unchecked apps permanently unable to reappear as checkboxes on the admin site. If a future "an app that got hidden can't be found again" bug shows up anywhere, check *every* PackageManager call in that code path for this flag, not just the first one you find.
- **A real boot-loop incident happened**: an earlier fix used a completely unfiltered `pm.getInstalledApplications(0)` for the suspend/enforcement loop, which included core OS/system packages - a restrictive allowlist suspended essential system components and crashed the phone into a boot loop, recovered via `adb reboot recovery`. `controllablePackages()`'s current design (explicit `SAFE_SYSTEM_PACKAGES` allowlist + `FLAG_SYSTEM` filter) must never go back to a broader heuristic. Under-inclusion (missing an edge-case app) is an acceptable tradeoff; over-inclusion touching core OS packages is not, ever. GrapheneOS's own `Auditor` (`app.attestation.auditor`) and `Info` (`app.grapheneos.info`) apps are both in this allowlist now - a parent should be able to restrict them like any other pre-installed app with a real UI.
- **Reading `WifiManager.isWifiEnabled`/calling `setWifiEnabled` needs `ACCESS_WIFI_STATE`/`CHANGE_WIFI_STATE` declared in the manifest even for Device Owner** - Device Owner exempts the app from the API 29+ restriction on *who* can toggle WiFi, but that's a separate concern from the base permission needing to be declared at all. Missing this crashed `QuickControlsActivity` with `SecurityException` the instant WiFi was included in a device's `quickControlsMask`, since `isWifiEnabled()` was called unguarded in `onCreate()`. Both `QuickControls.isWifiEnabled`/`setWifiEnabled` now also have defensive try/catch matching the rest of the file, as a second line of defense.
- **`LOCK_TASK_FEATURE_KEYGUARD` does nothing if the phone's own OS-level screen lock is "None"/swipe** - it only re-enables *whatever lock method is already configured*, it doesn't provide one of its own. Don't diagnose "lock screen checkbox isn't working" as a code bug without first confirming the test device actually has a PIN/pattern set in system Settings.
- **`LOCK_TASK_FEATURE_NOTIFICATIONS` does not bring back Quick Settings tiles** - confirmed on real hardware (GrapheneOS/Pixel 4a): with only this feature enabled, the notification shade pulls down and shows notifications, but there are zero QS tiles (no WiFi/Bluetooth/etc. tile row at all), and no combination of the other feature bits changes that. So Quick Settings tiles are apparently just unreachable during Lock Task mode on this platform, full stop - there's no bit that restores them, and the docs' implication that this feature covers "the expandable notification shade" broadly is misleading in practice. Any WiFi/Bluetooth toggling a kid does while pinned is happening through the Settings app (if allowlisted), not Quick Settings - the `wifi_mode`/`bluetooth_mode` `UserManager` restrictions in `AppEnforcer.applyRadioRestrictions()` gate the underlying action itself and work the same regardless of which UI reaches it, which is exactly why they still work even though QS tiles don't render.
- **A VPN app's own managed-config restriction only binds that app's own UI - not its own Quick Settings tile, and not any other OS surface.** Confirmed via live testing: Tailscale's `ForceEnabled` managed-config key (pushed via `setApplicationRestrictions`, see `AppEnforcer.applyVpnRestrictions`) successfully disables the in-app disconnect control, but Tailscale's own QS tile (published outside Lock Task mode, i.e. whenever the full shade is reachable) ignores it entirely and can still disconnect the VPN - apparently a separate code path in Tailscale's own app that doesn't check the same flag its main UI does. This generalizes: don't assume a third-party app's MDM/managed-config cooperation covers every surface it exposes, including its own tiles. The real fix for "this must stay connected, full stop" is `DevicePolicyManager.setAlwaysOnVpnPackage(admin, pkg, lockdownEnabled = true)`, enforced by the OS's connectivity stack directly and independent of the app's cooperation - now applied alongside `ForceEnabled` in `applyVpnRestrictions`, not instead of it.
- **The general lesson from the above**: since *any* third-party app can publish its own Quick Settings tile that ignores our restrictions, Quick Settings itself isn't a safe surface to rely on for anything kid-facing, even outside the VPN case specifically. Rather than chase this app-by-app, the launcher has its own swipe-left-from-home "Quick Controls" screen (`ui/quickcontrols/QuickControlsActivity`) - a small, admin-curated set of toggles (WiFi, Bluetooth, brightness) built entirely on direct, silent Device-Owner APIs (`server/QuickControls.kt`), never Android's native QS tiles or `Settings.Panel.*` intents. This is the intended way for a kid to reach these controls; Quick Settings access itself is assumed permanently unsafe to expose while restrictions matter. Each of the WiFi/Bluetooth rows also has a "Manage networks"/"Manage devices" link (enabled only while that radio is on) into `WifiNetworksActivity`/`BluetoothDevicesActivity` - real scan/connect/forget screens, still built entirely on `QuickControls.kt`'s Device-Owner APIs, for the same reason.
- **`WifiManager`'s scan/connect/configured-network APIs (`startScan`, `getScanResults`, `getConfiguredNetworks`, `addNetworkPrivileged`) all hard-require the phone's system-wide Location toggle to be on**, confirmed live via `WifiService`'s own `SecurityException("Location mode is disabled for the device")` - thrown regardless of any app permission held, including `NEARBY_WIFI_DEVICES` with `neverForLocation` (that flag only covers the runtime-permission side, not this separate, unconditional platform check). `WifiNetworksActivity` works around this by silently flipping Location on for just that screen's lifetime via `DevicePolicyManager.setLocationEnabled` (Device-Owner-only, no Settings/dialog) and restoring whatever it was on exit - not a permanent change to the phone's Location setting. If a future "can't see any networks" report shows up, check this first before assuming a code bug.
- **There is no public `WifiManager.connect(int, ActionListener)` or `BluetoothDevice.isConnected()`/`connect()`/`disconnect()`** despite being documented in AOSP source - they're `@SystemApi`/hidden and simply aren't present in the public SDK jar this app compiles against (confirmed via `javap` against the real `android-36` platform jar, not assumed from docs). WiFi connection uses the public `enableNetwork(id, true)` instead, whose success only means the OS *accepted* the connect attempt, not that it actually associated - `WifiNetworksActivity` polls `scanWifiNetworks` afterwards and checks real connected state, since a wrong password shows up as a silent retry loop rather than a clean failure. The Bluetooth methods have no public replacement at all, so `QuickControls.kt` reflects into them (same pattern as `removeBond`), with the same fail-soft-on-any-OS-build handling as everywhere else in that file.
- **A `Handler`/other `Context`-dependent field initialized directly in a Kotlin property initializer (e.g. `private val handler = Handler(mainLooper)`) crashes on `Activity` construction** - property initializers run in the constructor, before `attachBaseContext`, so `Activity.mainLooper` (a `Context` method) throws `NullPointerException` on the still-null base context. Use the static `Looper.getMainLooper()` instead (no `Context` needed at all), or defer initialization into `onCreate()`.
- **`BLUETOOTH_SCAN` and `NEARBY_WIFI_DEVICES` both need `android:usesPermissionFlags="neverForLocation"`** in the manifest, or Android additionally requires the phone's Location toggle for scan results to come back at all (Bluetooth) or for the permission itself to be meaningfully granted (WiFi) - on top of, and separate from, the `setLocationEnabled` gotcha above for WiFi specifically.
- **`setAlwaysOnVpnPackage(..., lockdownEnabled = true)` for Tailscale without an exit node configured breaks all network connectivity, not just non-tailnet traffic** - confirmed live, and it's Tailscale's own documented behavior (github.com/tailscale/tailscale#12925, #1568), not something on our end to fix. Tailscale is a split-tunnel VPN: it only routes tailnet-destined traffic through its interface, not general internet traffic, unless an exit node is set. Lockdown forces *all* traffic through the VPN interface regardless of that - so with no exit node, Tailscale's tunnel has nowhere to send ordinary internet packets and they're just dropped. `applyVpnRestrictions` now only engages lockdown when `tailscaleExitNodeId` is also non-blank; `ForceEnabled` (the app-level restriction) still applies either way, since it doesn't have this failure mode. Don't ever let an admin-facing "require this VPN" toggle enable OS-level lockdown independent of exit-node state again - it's a guaranteed footgun, not a maybe.
- **`adb shell dpm set-device-owner <pkg>/.RelativeReceiver`** resolves the relative component name against the wrong base when `applicationIdSuffix` is set (debug builds: installed package `com.kidslauncher.mdm.debug` vs. Kotlin namespace `com.kidslauncher.mdm`) - always pass the fully-qualified receiver class name.
- **Reading private SharedPreferences via `adb shell run-as <debuggable-pkg> cat /data/data/<pkg>/shared_prefs/<pkg>_preferences.xml`** works without root on debug builds - useful for verifying persisted state directly instead of guessing from behavior. Note the file is named after the *installed package name*, not the Kotlin namespace.
- **`dumpsys activity activities` (search "LockTaskController") and `dumpsys statusbar` (`mDisabled1`/`mDisabled2`)** are ground truth for whether kiosk mode is actually engaged right now - more reliable than trusting the cached `kiosk_enabled` preference, which only reflects what the last `AppEnforcer.apply()` call computed and can be stale.
- **Kotlin top-level `private` is file-scoped, not package-scoped** - use `internal` to share a helper (e.g. `controllablePackages`) across files in the same package. This applies to `private` on an object/class member too (scoped to that type, not the file) - `QuickControls.selfGrantPermission` had to become `internal`, not stay `private`, for `LocateCommands.kt` to reuse it.
- **`DevicePolicyManager.setPermissionGrantState` re-issuing an already-granted permission retriggers GrapheneOS/Android's "your organization allows this app to access X" transparency notification every single call**, not just the first grant - so calling a self-grant helper unconditionally on every 2-minute sync produces a recurring notification the user can never actually dismiss for good. Always check `ContextCompat.checkSelfPermission` first and skip the grant call if already granted (see `QuickControls.selfGrantPermission`).
- **Android's location-in-use indicator fires on *any* `LocationManager` query that returns a fix - including the passive `getLastKnownLocation()` fallback, not just an active `getCurrentLocation()` fetch.** First throttled just the active fetch (`ACTIVE_LOCATION_FETCH_THROTTLE_MS` = 10 minutes, only a `ring`/`locate` command forces it sooner), but the indicator kept appearing on every sync anyway - the passive fallback path was still being reached, and still touching `LocationManager`, on every throttled-skip cycle. Fixed by having the app keep its own cached copy of the last fix obtained (`cached_location_json` preference, `LocateCommands.loadCachedFix`/`saveCachedFix`) - a skipped cycle now returns that directly with zero `LocationManager` calls at all, so the indicator only appears on a due/forced cycle, not every sync. If a future "indicator/permission-usage still showing up too often" bug shows up anywhere in this app, check *every* path that could reach the relevant manager, not just the obvious one - same lesson as the `MATCH_UNINSTALLED_PACKAGES` gotcha above.
- **`LocationManager.getLastKnownLocation()` is purely passive** - it only returns a cached fix from whatever last requested one for any reason, and returns `null` forever if nothing ever has. It is not a "get me a location" call. For an actual on-demand fix, use `LocationManager.getCurrentLocation()` (API 30+, callback-based - bridge into a `suspend` function with `suspendCancellableCoroutine` + a `withTimeoutOrNull` wrapper) and only fall back to the cached value on timeout. `LocateCommands.currentLocation` does this; don't revert to a bare `getLastKnownLocation` call for this feature.
- **`AppInstallReceiver`'s manifest entry declared no `<intent-filter>`, and `AppInstaller.installSilently` targeted it via an *implicit* action intent (`Intent(APP_INSTALL_ACTION).setPackage(context.packageName)`) rather than an explicit component - so the `PackageInstaller.Session.commit()` result broadcast had nothing to resolve against and was silently dropped, every single time, for this app's entire history.** This is the actual, original cause of the self-update loop below - not the `apply()`-vs-`commit()` timing issue (real, and worth fixing, but not what was actually happening here): `recordInstalled`/`recordFailed` never fired even once, on any build, because the receiver was never reachable at all. No exception, no log line, nothing - the broadcast just vanished. Fixed by having `AppInstaller` target `AppInstallReceiver` explicitly (`Intent(context, AppInstallReceiver::class.java)`), which doesn't depend on any manifest intent-filter. **The general lesson**: a `PendingIntent.getBroadcast` built from an implicit action + `setPackage()`, aimed at a manifest receiver with no matching `<intent-filter>`, fails completely silently on modern Android - no crash, no log, the broadcast just never arrives. For any app-internal-only receiver (never meant to be triggered by anything outside your own `PendingIntent`), target it explicitly by component instead of relying on implicit action resolution; don't assume "it's registered in the manifest" means "it's reachable."
- **The kapt-generated `LauncherPreferences` setters all write via `SharedPreferences.Editor.apply()` (async, fire-and-forget), which is a real hazard for any write that races an imminent process death** - fixed for `TrackedAppUpdateState.save` and `LocateCommands`'s two location-cache writes (`saveCachedFix`/`saveLastActiveFetchAt`), all of which now bypass the generated setter and write directly via `PreferenceManager.getDefaultSharedPreferences(context).edit().put...(key, ...).commit()` (synchronous). Worth keeping even though the intent-filter bug above turned out to be the real cause of the self-update loop specifically - this is still a real hazard for anything written right before a self-update-triggered process kill.
- **Sideloading over a device that's already running the self-update system produces exactly one extra self-reinstall cycle, and this is expected, not a regression** (now that the intent-filter bug above is fixed and `recordInstalled` can actually fire) - `TrackedAppUpdateState` only ever gets populated by `AppInstallReceiver` reacting to a real self-triggered install; an `adb install -r` never touches it. So a sideloaded build always starts from "no record of ever installing anything," sees whatever the server currently advertises as the latest release as "new," and reinstalls itself once via its own mechanism - which is what finally lets `recordInstalled` populate and stabilizes it from then on. The tell for diagnosing this specific case (vs. a real bug) is checking the device's actual `tracked_app_update_state` preference (`adb shell run-as <pkg> cat .../shared_prefs/<pkg>_preferences.xml`) - if the key is entirely absent, no self-update has ever successfully completed on this device. **Also watch for `INSTALL_FAILED_VERSION_DOWNGRADE` in `adb logcat` around a self-update attempt** (`PackageInstallerSession` tag) - if the server's cached tracked-app release was fetched (via "Check now" or the hourly poll) *before* a just-pushed CI build finished uploading to the rolling `pre-release` tag, it caches a stale, older asset; Android correctly refuses to "downgrade" over a newer sideloaded build, and since the failure happens at session verification (before `AppInstaller`'s receiver would even be invoked), nothing gets recorded either - it'll keep retrying the same doomed download until "Check now" is clicked again *after* the real build is actually live on GitHub.
- **A foreground service must call `Service.startForeground()` immediately in `onCreate()`, unconditionally, before any other setup logic** - as of API 34, `Context.startForegroundService()` requires the matching `startForeground()` call to land promptly or the OS throws `ForegroundServiceDidNotStartInTimeException` and kills the app. `CommandListenerService` (holds the SSE connection for instant command push, see the server's own CLAUDE.md) calls `startForeground()` as literally the first line of `onCreate()`, before checking whether the device is even enrolled yet.

## Established discipline

**Never install a locally-built APK.** After a lost-signing-key incident, the rule is: push to GitHub, let `.github/workflows/android.yml` build and sign with the repo's `ANDROID_DEBUG_KEYSTORE` secret, `gh release download pre-release --pattern "*.apk"`, verify the signature with `apksigner verify --print-certs` against the known-good keystore fingerprint before every `adb install -r`, and bump `versionCode`/`versionName` in `app/build.gradle.kts` every time. The `pre-release` GitHub Release is a single rolling tag (always overwritten, `allowUpdates: true`) representing the latest `master` build - not a growing release history.

## Current status (2026-08-04)

All planned client-side functionality is built and confirmed working live on the physical test phone (Pixel 4a 5G GrapheneOS, adb serial `0A031JECB05961`): enrollment, allowlist enforcement, kiosk mode with the full lock-task feature bitmask, bedtime/screen-time schedule, WiFi/Bluetooth restrictions, offline override PIN, Settings PIN-gate, pause-all-restrictions kill-switch, required-Tailscale enforcement (managed-config + always-on lockdown once an exit node is set), self-update through the unified tracked-app path, and GitHub-Releases app tracking/auto-install. Repo is public, GPLv3 (plus preserved MIT for the inherited app-list code). That test phone hit a real post-reboot lockout incident (GrapheneOS's auto-reboot-after-inactivity + kiosk mode suppressing the keyguard by default + this app being the exclusive enforced Home app with no direct-boot awareness = no way to unlock at all) - see the server's own CLAUDE.md gotcha entry; fixed by forcing `LOCK_FEATURE_KEYGUARD` on server-side, no client change needed.

**Quick Controls' WiFi/Bluetooth network+device pickers** (`WifiNetworksActivity`/`BluetoothDevicesActivity`) are built and live-verified: Bluetooth scan/pair/forget/connect confirmed working end-to-end; WiFi scan/connect/forget confirmed working after the `setLocationEnabled` fix above (was returning empty results / `SecurityException` before that). Not yet tested live: connecting to a WPA3-only network, and the Bluetooth connect/disconnect reflection path on an already-paired device (both should work per the code, just not yet exercised on real hardware).

**QR-code zero-touch provisioning** (`kid-phone-server`'s `/devices/provision`) works as designed on non-GMS devices, but a live attempt on a real GMS-certified device (Motorola Moto G Play 2024, Android 14) failed during the Device-Owner-provisioning step specifically - the same APK installs fine as a normal sideload on that device afterward, ruling out Play Protect blocking the app itself. Leading theory (not yet confirmed via logs - no adb access reachable before `ManagedProvisioning` resets back to OOBE on failure): Google restricts the zero-touch/QR Device-Owner flow specifically to Play-Store-sourced DPCs on GMS-certified hardware, separate from whatever gate blocks a plain sideload install. A release-signed (vs. debug-signed) build would likely reduce generic Play Protect friction elsewhere but probably wouldn't fix this specific failure if the theory is right, since it isn't about signing/trust - manual `adb shell dpm set-device-owner ...` remains the reliable path on any GMS device.

**Known open bug**: the swipe-left-from-home gesture into Quick Controls is intermittently unreliable ("sometimes doesn't register, seems random") - reported once, not yet reproduced/root-caused; the gesture-detection code itself reads as correct on inspection, so this needs live repro/logging to actually diagnose rather than a further code guess.

**Find My Device** (`server/LocateCommands.kt`, `server/CommandListenerService.kt`, `server/StopRingReceiver.kt`) is built, currently at `v0.7.1`, and was live-tested once against the real client after the initial `v0.7.0` ship. That pass found six issues, all addressed in `v0.7.1` (server's own CLAUDE.md has the same list from the other side): the recurring-notification and empty-map bugs above, the map-CSS overlap (server-side template fix, not client), ring loudness (`ring` now also forces `RINGER_MODE_NORMAL` when notification-policy access allows it, and raises `STREAM_RING`/`STREAM_NOTIFICATION`/`STREAM_MUSIC` alongside `STREAM_ALARM`, not just `STREAM_ALARM` alone), a mid-testing request for a way to stop an active ring (`StopRingReceiver` + a notification button on-device, `stop_ring` command + a server-side button), and the 2-minute poll delay for ring/lock/stop_ring (now pushed near-instantly via `CommandListenerService`, a permanent foreground service holding an SSE connection open against the server's `/api/devices/commands/stream`, using `okhttp-sse`'s `EventSource`).

**Confirmed live post-v0.7.1**: SSE push delivers ring near-instantly (sub-second, observed directly) with a stable long-lived connection; stop-ring works from both the device notification and the server button. **v0.7.2 fixed a real self-update bug** found during that same live pass: `TrackedAppUpdateState.recordInstalled` wrote through the generated preference setter (`apply()`, async), which routinely lost the write to the SIGKILL that follows a successful self-update - the launcher was stuck reinstalling the identical build every 15-30s, killing `CommandListenerService` each time (see the `apply()`-vs-`commit()` gotcha above). **v0.7.4 fixed the location-in-use indicator/slow-sync complaint** (see the location-caching gotcha above). **v0.7.5** pushes regular policy saves over SSE too (not just Find My Device commands, see the server's own CLAUDE.md) and relaxes the background poll from 2 to 5 minutes now that push covers the "make it happen now" case for both. Still not verified live: whether the map shows real location data, whether ring is perceptibly louder, whether `CommandListenerService`'s persistent notification behaves reasonably long-term, and whether the `ACCESS_BACKGROUND_LOCATION` self-grant is actually succeeding (diagnostic log line: `LocateCommands`, `"currentLocation: ACCESS_BACKGROUND_LOCATION granted=..."`). **Not started**: notification listener / message monitoring, DNS-level browsing restriction, tamper-resistant/launcher-watchdog persistence (auto-restart on crash/kill), real server-to-device push (currently 2-minute polling - deliberately not FCM, this project avoids Google/Play Services by design).
