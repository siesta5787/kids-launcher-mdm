# Kids Launcher — Project Context for Claude Code

## What this is

An Android home screen for a kid's phone that is also, in the same process, the [Device Owner](https://developer.android.com/work/dpc/build-dpc) parental-control agent. Package `com.kidslauncher.mdm`. It speaks directly to [`kid-phone-server`](https://github.com/siesta5787/kid-phone-server) (a separate repo) - there is no other server, protocol, or MDM stack involved; an earlier prototype used something else entirely and has been fully retired.

Originated as a fork of Josia Pietsch's µLauncher, itself descended from Finn Glas's Launcher, but almost nothing of that lineage remains functionally: the gesture-binding system, Minimalist Mode (as an optional toggle), torch, private-space lock, and audio-track controls were all removed. What's still genuinely shared is the app-list screen (`ui/list/`, `apps/`) - see `LICENSE-MIT-UPSTREAM`. Don't describe this project as "a fork" in user-facing copy; it's its own thing now built on a small inherited component, not vice versa.

## Tech stack

Kotlin, single Gradle module (`app/`). `minSdk = 34`, `compileSdk`/`targetSdk = 36`. Retrofit + kotlinx.serialization (`JsonNamingStrategy.SnakeCase`, matching the server's plain snake_case JSON) for the device-facing API client in `server/`. `androidx.preference` for Settings, `eu.jonahbauer.android.preference.annotations` (kapt-generated) for the typed `LauncherPreferences` accessor API.

**One Java file**: `preferences/LauncherPreferences$Config.java` - not a choice made in this fork, Josia Pietsch wrote it in Java originally (Sept 2024). It's the annotation config kapt reads to generate the real `LauncherPreferences` class every `mdm.xxx()` call in the codebase goes through - keep editing it in Java when adding new preference entries rather than converting it, since deeply-nested annotation arrays through kapt's Kotlin→Java stub bridge is a real source of subtle bugs that writing it directly in Java sidesteps.

## Architecture

- **Device Owner is the whole point.** `MdmDeviceAdminReceiver` + `dpm.isDeviceOwnerApp()` gate every enforcement call in `server/AppEnforcer.kt` - it's a no-op if not device owner, so it's safe to ship before a phone is actually provisioned.
- **`server/MdmSyncWorker.kt`** is the heartbeat: self-chains one-time `WorkManager` requests every 2 minutes (not `PeriodicWorkRequest`'s 15-minute floor - too slow for a parent to see a change land) to fetch policy, evaluate the lock decision, call `AppEnforcer.apply()`, and report status. `performMdmSync()` is also called directly by the Settings "Sync now" button and returns `Boolean` (whether it actually reached the server) so that button can show an honest success/failure toast.
- **`server/AppEnforcer.kt`** is the enforcement engine: suspends/hides packages not on the allowlist, engages/disengages lock-task kiosk mode (only when both an allowlist AND `kioskDesired` are set - never pins with zero allowed packages), applies the `lockTaskFeatures` bitmask, and applies WiFi/Bluetooth `UserManager` restrictions. `controllablePackages()` is the safety-critical bit - see gotchas below.
- **Offline override PIN** (`server/OfflineOverride.kt`): PBKDF2-HMAC-SHA256 verified fully offline against a hash+salt cached from the last successful sync. `verifyPin()` (pure verification, tracks failed attempts/lockout) is separate from `activate()` (the actual "lift restrictions for 2 hours" side effect) specifically so the Settings PIN-gate can reuse verification without also triggering an unwanted override.
- **Settings is PIN-gated** (`ui/settings/SettingsActivity.kt`) behind the same PIN if one's configured - shown as a non-cancelable modal dialog over the normally-inflated (but `INVISIBLE` until verified) content, not by deferring `binding` initialization, because `UIObjectActivity`'s `onStart()` unconditionally calls `setOnClicks()` which needs `binding` to already exist.
- **`restrictions_paused`** is a separate, manually-toggled kill-switch (unlike the PIN override, does *not* auto-clear on sync or after a timer) - an emergency escape hatch if a policy or launcher update ever ships something broken. Toggling it in Settings re-runs `AppEnforcer.apply()` and `reevaluateLockReasonFromCache()` immediately and offline, rather than waiting for the next sync.
- **`LockActivity.kt`** is the full-screen bedtime/screen-time block, with a visible (not hidden-behind-a-gesture) "Enter unlock code" button - the PIN itself is the security boundary, not the button's obscurity.
- **Silent self-update** via `LauncherUpdater.kt`'s `PackageInstaller` flow (requires Device Owner) - `MdmSyncWorker` checks for a newer server-hosted release every sync and installs it with no user interaction. A version that already failed to install (e.g. signing-certificate mismatch) is cached in `last_failed_update_version_code` so it isn't retried every 2 minutes forever.

## Non-obvious gotchas (hit for real, more than once in some cases)

- **`PackageManager` query methods silently exclude apps hidden via `dpm.setApplicationHidden()` unless you pass `MATCH_UNINSTALLED_PACKAGES`.** This bit `AppEnforcer.controllablePackages()`'s `getInstalledApplications()` call *and*, separately, `MdmSyncWorker.collectInstalledApps()`'s `getApplicationInfo()` call one level deeper - fixing only the first still left unchecked apps permanently unable to reappear as checkboxes on the admin site. If a future "an app that got hidden can't be found again" bug shows up anywhere, check *every* PackageManager call in that code path for this flag, not just the first one you find.
- **A real boot-loop incident happened**: an earlier fix used a completely unfiltered `pm.getInstalledApplications(0)` for the suspend/enforcement loop, which included core OS/system packages - a restrictive allowlist suspended essential system components and crashed the phone into a boot loop, recovered via `adb reboot recovery`. `controllablePackages()`'s current design (explicit `SAFE_SYSTEM_PACKAGES` allowlist + `FLAG_SYSTEM` filter) must never go back to a broader heuristic. Under-inclusion (missing an edge-case app) is an acceptable tradeoff; over-inclusion touching core OS packages is not, ever.
- **`LOCK_TASK_FEATURE_KEYGUARD` does nothing if the phone's own OS-level screen lock is "None"/swipe** - it only re-enables *whatever lock method is already configured*, it doesn't provide one of its own. Don't diagnose "lock screen checkbox isn't working" as a code bug without first confirming the test device actually has a PIN/pattern set in system Settings.
- **`LOCK_TASK_FEATURE_NOTIFICATIONS` does not bring back Quick Settings tiles** - confirmed on real hardware (GrapheneOS/Pixel 4a): with only this feature enabled, the notification shade pulls down and shows notifications, but there are zero QS tiles (no WiFi/Bluetooth/etc. tile row at all), and no combination of the other feature bits changes that. So Quick Settings tiles are apparently just unreachable during Lock Task mode on this platform, full stop - there's no bit that restores them, and the docs' implication that this feature covers "the expandable notification shade" broadly is misleading in practice. Any WiFi/Bluetooth toggling a kid does while pinned is happening through the Settings app (if allowlisted), not Quick Settings - the `wifi_mode`/`bluetooth_mode` `UserManager` restrictions in `AppEnforcer.applyRadioRestrictions()` gate the underlying action itself and work the same regardless of which UI reaches it, which is exactly why they still work even though QS tiles don't render.
- **`adb shell dpm set-device-owner <pkg>/.RelativeReceiver`** resolves the relative component name against the wrong base when `applicationIdSuffix` is set (debug builds: installed package `com.kidslauncher.mdm.debug` vs. Kotlin namespace `com.kidslauncher.mdm`) - always pass the fully-qualified receiver class name.
- **Reading private SharedPreferences via `adb shell run-as <debuggable-pkg> cat /data/data/<pkg>/shared_prefs/<pkg>_preferences.xml`** works without root on debug builds - useful for verifying persisted state directly instead of guessing from behavior. Note the file is named after the *installed package name*, not the Kotlin namespace.
- **`dumpsys activity activities` (search "LockTaskController") and `dumpsys statusbar` (`mDisabled1`/`mDisabled2`)** are ground truth for whether kiosk mode is actually engaged right now - more reliable than trusting the cached `kiosk_enabled` preference, which only reflects what the last `AppEnforcer.apply()` call computed and can be stale.
- **Kotlin top-level `private` is file-scoped, not package-scoped** - use `internal` to share a helper (e.g. `controllablePackages`) across files in the same package.

## Established discipline

**Never install a locally-built APK.** After a lost-signing-key incident, the rule is: push to GitHub, let `.github/workflows/android.yml` build and sign with the repo's `ANDROID_DEBUG_KEYSTORE` secret, `gh release download pre-release --pattern "*.apk"`, verify the signature with `apksigner verify --print-certs` against the known-good keystore fingerprint before every `adb install -r`, and bump `versionCode`/`versionName` in `app/build.gradle.kts` every time. The `pre-release` GitHub Release is a single rolling tag (always overwritten, `allowUpdates: true`) representing the latest `master` build - not a growing release history.

## Current status (2026-07-31)

All planned client-side functionality is built and confirmed working live on the physical test phone (Pixel 4a 5G, adb serial `0A031JECB05961`): enrollment, allowlist enforcement, kiosk mode with the full lock-task feature bitmask, bedtime/screen-time schedule, WiFi/Bluetooth restrictions, offline override PIN, Settings PIN-gate, pause-all-restrictions kill-switch, and silent self-update. Repo is public, GPLv3 (plus preserved MIT for the inherited app-list code).

**Not started**: notification listener / message monitoring, DNS-level browsing restriction, tamper-resistant/launcher-watchdog persistence (auto-restart on crash/kill), real server-to-device push (currently 2-minute polling - deliberately not FCM, this project avoids Google/Play Services by design). See the root `PROJECT_CONTEXT.md` for the full staged plan on the messaging/monitoring pieces specifically.
